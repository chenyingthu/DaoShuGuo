# 受控枚举与状态规范

## 1. 文档目的

本文件用于定义项目第一阶段各类对象的受控枚举和值域约束。

如果没有统一状态和枚举规范，后续最容易出现的问题不是字段不够，而是：

- 同一状态写成多种文本
- 同一含义在不同对象里用不同词
- 判断逻辑无法复用
- 统计和回溯变得不可信

## 2. 总原则

### 2.1 枚举先少后多

第一阶段优先使用最小必要枚举集，不追求覆盖所有未来可能性。

### 2.2 语义稳定

一旦某个枚举值进入核心对象，就不应频繁改变含义。

### 2.3 对象内聚

不同对象可以有不同状态值，不要为了统一而硬凑。

### 2.4 人类可读

枚举值应清晰、直白，不要使用含糊缩写。

## 3. 通用状态字段

很多对象会带 `status`，但 `status` 不等于所有对象共用同一组枚举。

建议将状态分为三层：

1. 生命周期状态
2. 运行状态
3. 审核或成熟度状态

## 4. Task 状态建议

### 4.1 推荐枚举

- `draft`
- `active`
- `blocked`
- `archived`
- `invalid`

### 4.2 语义说明

- `draft`
  任务已建立，但尚未进入正式执行。

- `active`
  任务处于当前有效研究阶段。

- `blocked`
  任务因条件不足暂时无法推进。

- `archived`
  任务已完成或停止，进入归档。

- `invalid`
  任务定义被证明不成立或不适合继续。

## 5. Evaluator 状态建议

### 5.1 推荐枚举

- `draft`
- `ready`
- `deprecated`
- `invalid`

### 5.2 语义说明

- `draft`
  evaluator 已定义但尚未达到可执行标准。

- `ready`
  evaluator 可独立执行并参与正式比较。

- `deprecated`
  evaluator 仍可读取，但不推荐继续使用。

- `invalid`
  evaluator 被证明存在严重问题，不应用于正式判断。

## 6. Run 状态建议

### 6.1 推荐枚举

- `queued`
- `running`
- `completed`
- `blocked`
- `failed_experiment`
- `insufficient_evidence`
- `cancelled`

### 6.2 语义说明

- `queued`
  已创建但尚未开始执行。

- `running`
  当前正在执行中。

- `completed`
  运行完成并产出结果摘要。

- `blocked`
  因外部条件或内部依赖暂时卡住。

- `failed_experiment`
  已执行但未得到有效结果。

- `insufficient_evidence`
  结果可能存在，但证据不足以支撑有效判断。

- `cancelled`
  该次运行被人工或系统中止。

### 6.3 注意

`completed` 不代表“成功创新”，只代表“运行结束且有结果”。

## 7. Skill 成熟度建议

### 7.1 推荐字段

建议 `status` 与 `maturity_level` 分离。

### 7.2 Skill status 建议

- `draft`
- `active`
- `deprecated`
- `retired`

### 7.3 Skill maturity_level 建议

- `candidate`
- `validated`
- `stable`

### 7.4 语义说明

- `candidate`
  已实现，但验证不足。

- `validated`
  已经通过明确运行或 evaluator 验证。

- `stable`
  已在多个场景或多次运行中表现可靠。

## 8. Cognition 类型与状态建议

### 8.1 Cognition type 建议

- `candidate`
- `stable`
- `failure`
- `conflict`

### 8.2 Cognition confidence_level 建议

- `low`
- `medium`
- `high`

### 8.3 Cognition promotion_status 建议

- `proposed`
- `under_review`
- `accepted`
- `rejected`

### 8.4 语义说明

- `candidate`
  初步认知，尚未稳定。

- `stable`
  已有较强证据支撑的认知。

- `failure`
  来自失败路径的负向认知。

- `conflict`
  与现有认知发生冲突的认知对象。

## 9. Taste Assessment 等级建议

### 9.1 grade 枚举

- `tuoyu`
- `zhuoshi`
- `diaomu`
- `huimo`

### 9.2 review_status 建议

- `draft`
- `reviewed`
- `locked`

### 9.3 语义说明

- `draft`
  初步分级，尚可调整。

- `reviewed`
  已完成本轮审核。

- `locked`
  已作为正式分级结果写回。

## 10. Report 类型建议

### 10.1 report_type 枚举

- `discussion_memo`

### 10.2 audience 建议

- `internal_team`
- `advisor`
- `research_archive`
- `external_academic`

## 11. 比较方向建议

Evaluator 指标中的 `direction` 建议枚举：

- `higher_is_better`
- `lower_is_better`
- `target_is_best`
- `constraint_only`

### 11.1 语义说明

- `higher_is_better`
  数值越高越好。

- `lower_is_better`
  数值越低越好。

- `target_is_best`
  越接近目标值越好。

- `constraint_only`
  只用于约束判定，不直接纳入优化优劣。

## 12. 引用类型建议

如果后续需要对引用再细分，建议先支持：

- `latest`
- `versioned`
- `snapshot`

### 12.1 语义说明

- `latest`
  指向对象当前最新稳定版。

- `versioned`
  指向特定版本。

- `snapshot`
  指向运行时实际使用快照。

## 13. 第一阶段最小枚举集

第一阶段若要尽量克制，建议至少统一以下枚举：

1. `Task.status`
2. `Evaluator.status`
3. `Run.run_status`
4. `Skill.maturity_level`
5. `Cognition.cognition_type`
6. `Cognition.confidence_level`
7. `Taste Assessment.grade`
8. `Report.report_type`
9. `Metric.direction`

## 14. 演化规则

枚举值演化建议遵循：

1. 优先新增，不轻易改名。
2. 若改名，必须保留迁移映射。
3. 若删除，先弃用再移除。

## 15. 设计警戒线

以下情况说明枚举体系开始腐化：

1. 同一状态同时出现 `done`、`completed`、`finished`。
2. 把高层判断词写进运行状态，例如 `excellent`。
3. 用自然语言段落替代结构化等级值。
4. 因为怕束缚而完全不用受控枚举。

若出现这些情况，应先统一值域，再继续扩张 schema。
