# 数据契约设计总纲

## 1. 文档目的

本文件用于定义本项目数据契约设计的总原则、核心对象边界、抽象层次和扩展策略。

它不是具体字段表，而是所有后续 schema 设计必须共同遵守的顶层约束。

## 2. 为什么数据契约是核心基础设施

本项目不是一次性脚本集合，而是一个会持续积累以下资产的研究系统：

1. 技能
2. 认知
3. 成效
4. 运行证据
5. 方法论观察

如果没有稳定的数据契约：

- 技能无法可靠复用
- 认知无法可靠回链
- evaluator 无法独立演进
- 任务之间无法比较
- 后继者无法复盘系统是如何得出结论的

因此，数据契约不是附属实现细节，而是系统可积累、可研究、可扩展的基础。

## 3. 数据契约的核心目标

本项目的数据契约必须同时满足以下目标：

### 3.1 结构清晰

不同对象必须有明确边界，不能把任务、结果、认知、报告混成一个大文档。

### 3.2 可回链

高层结论必须能追溯到任务、技能、实验和 evaluator 结果。

### 3.3 可扩展

第一阶段先支持最小闭环，但后续要能扩展到：

- 多任务
- 多 evaluator
- 多技能版本
- 认知冲突
- 多轮运行比较
- 多 Agent 行为观察

### 3.4 可兼容

后续 schema 演化时，旧数据不能立刻失效，至少要保证可迁移或可降级读取。

### 3.5 可审计

必须能支持追问：

- 这个结果是怎么来的
- 为什么认为它有效
- 为什么形成这条认知
- 为什么只能评为“雕木”而不是“琢石”

## 4. 抽象原则

### 4.1 对象优先，不以文件优先

先定义“系统里有哪些对象”，再决定这些对象落成多少文件。

不允许因为“写一个 JSON 方便”就把多个不同对象压在一起。

### 4.2 契约优先，不以实现优先

数据契约必须独立于底层实现方式。

例如：

- 即便今天用 Markdown 记录认知卡片，认知对象本身仍应有稳定语义结构。
- 即便今天用本地脚本做 evaluator，evaluator 结果对象仍应独立于脚本实现。

### 4.3 主对象与派生对象分离

必须区分：

- 原始对象
- 派生对象
- 汇总对象

例如：

- 单次 evaluator 结果是原始对象
- 成果分级是派生对象
- 最终报告是汇总对象

不允许让汇总对象反过来成为原始事实来源。

### 4.4 身份与版本分离

每类核心对象都应区分：

- 对象身份
- 对象版本

例如技能 `skill_voltage_optimizer` 和其 `v0.1.0`、`v0.2.0` 是两个不同层次。

### 4.5 内容与证据分离

认知内容本身和支撑它的证据引用必须分开表达。

否则后续会出现“看起来像认知，但无法判断它是否可信”的问题。

## 5. 核心对象模型

后续所有具体 schema 都必须围绕以下核心对象展开。

### 5.1 Task

表示一个研究任务的定义对象。

负责回答：

- 研究什么
- 在什么边界下研究
- 目标是什么
- 基线是什么

### 5.2 Evaluator

表示一个成效评价对象。

负责回答：

- 怎样判断是否进步
- 用什么指标判断
- 与谁比较
- 判定标准是什么

### 5.3 Run

表示一次实际运行对象。

负责回答：

- 某次尝试具体做了什么
- 使用了哪些输入
- 产生了哪些结果
- 处于哪个状态

### 5.4 Skill

表示一个可复用执行能力对象。

负责回答：

- 这个能力是什么
- 输入输出是什么
- 适合什么场景
- 哪个版本有效

### 5.5 Cognition

表示一条认知对象。

负责回答：

- 获得了什么理解
- 证据来自哪里
- 适用边界是什么
- 与已有认知关系如何

### 5.6 Evidence Bundle

表示一组可回链证据对象。

负责回答：

- 这个高层结论依赖哪些底层事实
- 哪些文件、运行、结果和卡片组成了证据链

### 5.7 Taste Assessment

表示一轮成果分级对象。

负责回答：

- 本轮产出是玉、石、木还是墨
- 为什么这样分级
- 可以说到什么程度

### 5.8 Report

表示面向人类阅读的汇总表达对象。

负责回答：

- 这轮任务可以如何被诚实地讲述

Report 是表达层对象，不得反向定义事实层对象。

## 6. 对象之间的依赖方向

必须遵守以下依赖方向：

1. `Task` 定义任务
2. `Evaluator` 基于 `Task` 定义评价方式
3. `Run` 执行 `Task` 并使用 `Evaluator`
4. `Skill` 被 `Run` 调用或生成
5. `Cognition` 基于 `Run` 和 `Evaluator` 结果提炼
6. `Taste Assessment` 基于 `Run` 结果和 `Cognition` 形成
7. `Evidence Bundle` 绑定上述对象
8. `Report` 基于 `Evidence Bundle` 和 `Taste Assessment` 输出

不允许出现以下反向依赖：

- Report 决定 Taste Assessment
- Taste Assessment 决定 Evaluator 结果
- Cognition 决定原始 Run 事实

## 7. 最小对象边界要求

即使第一阶段只用本地文件，也必须保证以下对象逻辑上独立：

1. 任务定义
2. evaluator 定义
3. 单次运行记录
4. 技能注册记录
5. 认知卡片
6. 成果分级结果
7. 报告

如果它们被物理合并到少数文件中，也必须保留逻辑分区和稳定标识。

## 8. 扩展性设计原则

### 8.1 预留元信息区

每类对象都应允许存在：

- `metadata`
- `extensions`
- `tags`

这类扩展槽位用于后续添加非核心属性，而不破坏主结构。

### 8.2 区分必填与选填

第一阶段要严格控制必填字段，只保留闭环最需要的核心字段。

非核心信息应作为可选扩展，而不是一开始就写满。

### 8.3 区分稳定字段与实验字段

本项目本身在做研究，部分字段未来会频繁变化。

因此需要区分：

- 稳定字段：跨阶段都应保留
- 实验字段：某轮研究暂时加入，用于验证想法

### 8.4 支持多值引用

未来很多对象会是一对多关系：

- 一个任务对应多次运行
- 一个认知对应多条证据
- 一个技能对应多个适用场景

契约设计必须默认支持这种扩展。

## 9. 版本化原则

### 9.1 每类契约都必须有 schema 版本

后续每一类核心对象都必须显式带版本信息。

### 9.2 小改与大改区分

应区分：

- 向后兼容的小改
- 不兼容的大改

### 9.3 迁移优先于抛弃

如果 schema 发生演化，优先设计迁移路径，而不是让旧对象直接不可用。

### 9.4 运行记录不可事后重写事实

允许增加解释、补充元信息，但不应无痕改写已发生的实验事实。

## 10. 命名与标识原则

核心对象需要稳定标识。

标识设计应满足：

- 唯一
- 可读
- 可追踪
- 不过度耦合文件路径

建议后续将：

- 人类可读名
- 稳定 ID
- 版本号

区分表达，而不是混在一个字符串里。

## 11. 第一阶段设计边界

第一阶段不追求全能 schema，只追求闭环稳固。

因此第一阶段的数据契约设计应优先支持：

1. 单任务闭环
2. 单 evaluator
3. 单次和多次运行对比
4. 技能沉淀
5. 认知沉淀
6. 成果分级
7. 证据回链

第一阶段不强求：

- 复杂图关系序列化
- 多租户或远程服务设计
- 分布式存储
- 通用数据库建模

## 12. 设计警戒线

以下情况说明数据契约开始退化：

1. 同一个对象既写任务定义又写实验结果。
2. 报告文本被当成事实源。
3. 成果等级没有独立对象。
4. 认知没有证据引用。
5. 技能没有版本概念。
6. evaluator 与运行结果混在一起无法分离。

若出现这些情况，应先修复对象模型，再写具体字段。
