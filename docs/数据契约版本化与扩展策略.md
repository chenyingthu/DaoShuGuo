# 数据契约版本化与扩展策略

## 1. 文档目的

本文件用于定义本项目未来各类数据契约的版本化、兼容性、迁移和扩展规则。

本项目会长期演进，如果没有提前设计版本策略，后面所有积累都会因为 schema 变化而变脆。

## 2. 设计目标

版本化策略需要同时满足：

1. 允许第一阶段快速迭代。
2. 不破坏已沉淀的历史对象。
3. 为后续复杂功能扩展留空间。
4. 让后继者能理解“为什么这个对象长成这样”。

## 3. 三层版本概念

本项目中至少存在三层版本，不应混淆。

### 3.1 Schema Version

表示某类数据结构本身的版本。

例如：

- Task schema 的版本
- Skill schema 的版本
- Cognition schema 的版本

### 3.2 Object Version

表示某个对象内容的版本。

例如：

- 某个技能从 `v0.1.0` 演化到 `v0.2.0`
- 某个认知卡片被补充证据后形成新版

### 3.3 Runtime Revision

表示某次运行中对对象的临时快照或记录修订。

它不等同于对象的正式新版本。

## 4. 兼容性原则

### 4.1 读取优先

优先保证旧对象可以被解释、迁移或降级读取，而不是立刻失效。

### 4.2 写入慎重

新版本写入时应尽量明确：

- 使用了哪一版 schema
- 哪些字段是新加的
- 是否兼容旧消费者

### 4.3 删除最谨慎

删除字段是高风险动作。

若必须删除，应优先经历：

1. 标记弃用
2. 提供迁移说明
3. 保留兼容读取窗口

## 5. 字段演化规则

### 5.1 允许的低风险变更

- 新增可选字段
- 新增扩展区域
- 新增非关键枚举值
- 补充元信息字段

### 5.2 中风险变更

- 新增必填字段
- 调整字段语义
- 合并字段来源

这类变更必须附带迁移说明。

### 5.3 高风险变更

- 删除字段
- 改变核心对象边界
- 改变引用方向
- 让旧对象无法解释

这类变更应极其慎重，原则上不在没有充分理由时发生。

## 6. 扩展槽设计

为避免每次实验都重写 schema，建议在主要对象中预留扩展槽。

建议包括：

- `metadata`
- `extensions`
- `annotations`
- `experimental`

使用规则：

- 核心语义不要塞进扩展槽
- 实验性字段优先进入 `experimental`
- 稳定后再上升为正式字段

## 7. 稳定核心与实验边缘

每类对象都应分成两个圈层：

### 7.1 稳定核心

这些字段跨阶段都应相对稳定，例如：

- 对象身份
- 版本
- 基础状态
- 核心引用

### 7.2 实验边缘

这些字段用于当前阶段验证新机制，例如：

- 某个新型品味评分维度
- 某个 prompt 行为观测字段
- 某个尚未固化的认知关系

实验边缘允许变化更快，但不能污染稳定核心。

## 8. 引用策略

后续所有对象应优先通过稳定 ID 互相引用，而不是靠文件名或自然语言查找。

引用设计原则：

- 引用要指向稳定对象身份
- 需要时再补版本信息
- 引用要能支持一对多
- 允许保留“快照引用”和“最新引用”的区分

## 9. 时间维度策略

由于本项目要研究长期演化，数据契约需要显式考虑时间。

至少应支持表达：

- 创建时间
- 更新时间
- 首次观察时间
- 运行发生时间
- 版本生效时间

避免后续出现“知道结论，但不知道它是在什么时候形成的”。

## 10. 迁移策略

后续 schema 演化时，建议采用以下顺序：

1. 先定义新版 schema
2. 明确与旧版差异
3. 提供迁移映射规则
4. 用样本对象验证迁移
5. 再允许新数据写入新版

不要先改生产对象，再回头猜怎么迁移。

## 11. 与研究目标的关系

本项目不是普通业务系统，因此版本化除了支持工程稳定性，还要支持研究可比性。

也就是说，版本策略应支持回答：

- 不同阶段的 evaluator 差异是否影响结论
- 不同阶段的品味分级规则是否导致结果不可比
- 不同版本的技能是否真的带来了更高成效
- 认知对象的演化是补充证据，还是改变了含义

## 12. 第一阶段的最低要求

即使在第一阶段，也建议后续具体 schema 至少支持：

1. `schema_version`
2. `object_id`
3. `object_version`
4. `created_at`
5. `updated_at`
6. `metadata`

这几个元素会显著提高后续扩展的稳定性。

## 13. 禁止事项

以下做法会显著损害长期演进能力：

1. 把对象身份和文件路径绑定死。
2. 没有版本号就修改对象语义。
3. 用自然语言报告代替结构化演化记录。
4. 新增实验字段时直接污染核心字段区。
5. 在没有迁移规则时强行替换旧 schema。

## 14. 核心结论

好的版本化策略不是为了“显得专业”，而是为了让系统在多年演化后，仍然知道：

- 过去到底积累了什么
- 这些积累今天还能不能用
- 新旧对象之间到底是什么关系
