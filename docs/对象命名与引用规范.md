# 对象命名与引用规范

## 1. 文档目的

本文件用于定义项目中所有核心对象的命名、标识和引用规则。

在一个长期演进的研究系统中，很多混乱不是来自字段不够多，而是来自：

- 对象名字能看懂，但不稳定
- 文件路径可见，但不能充当身份
- 引用看似存在，但无法可靠回链

因此，本规范的目标是让系统在多年演进后仍然能回答：

- 这是谁
- 它的哪个版本
- 它和谁有关
- 当前引用的是“最新”还是“快照”

## 2. 设计原则

### 2.1 身份优先于路径

对象身份必须独立于文件路径。

文件路径可以变化，对象身份不应因此变化。

### 2.2 可读优先于压缩

ID 需要紧凑，但更重要的是可读和可审查。

不要为了短而把 ID 变成无意义随机串。

### 2.3 类型显式

对象标识应让人一眼看出大类，不应让 `task`、`run`、`skill` 混在一起。

### 2.4 快照与稳定身份分离

必须区分：

- 稳定对象身份
- 对象的某个版本
- 某次运行时刻的快照引用

## 3. 核心概念

### 3.1 Human Name

面向人类阅读的名称。

例如：

- `IEEE33无功优化最小闭环验证`
- `默认无功优化评估器`
- `弱网电压支撑经验认知`

Human Name 可读，但不稳定，不应用于机器唯一识别。

### 3.2 Object ID

稳定对象身份标识。

它表示“这是哪个对象”，不表示“这个对象的哪一版”。

### 3.3 Object Version

对象内容版本。

它表示“这个对象在什么版本状态下”。

### 3.4 Reference

对象之间的结构化引用。

引用必须明确：

- 指向谁
- 是否带版本
- 是否是快照

## 4. Object ID 总体规范

### 4.1 组成原则

建议使用以下结构：

`<type>.<scope>.<name>`

其中：

- `type` 表示对象类型
- `scope` 表示任务域、问题域或局部命名空间
- `name` 表示该对象在作用域内的稳定标识名

### 4.2 示例

- `task.power.ieee33_reactive_opt`
- `evaluator.power.ieee33_reactive_opt.default`
- `run.power.ieee33_reactive_opt.0001`
- `skill.power.reactive_optimizer`
- `cognition.power.weak_grid_voltage_support_rule`
- `taste.power.ieee33_reactive_opt.0001`
- `evidence.power.ieee33_reactive_opt.0001`
- `report.power.ieee33_reactive_opt.note_0001`

### 4.3 字符规范

建议：

- 小写英文
- 数字
- 下划线 `_`
- 点号 `.`

避免：

- 空格
- 中文作为稳定 ID 本体
- 特殊符号
- 含糊缩写

中文可以存在于 `title` 或 `display_name` 中，但不宜直接作为稳定 ID。

## 5. 各类对象的命名建议

### 5.1 Task

建议模式：

`task.<domain>.<problem_name>`

示例：

- `task.power.ieee33_reactive_opt`
- `task.power.microgrid_dispatch`

### 5.2 Evaluator

建议模式：

`evaluator.<domain>.<problem_name>.<variant>`

示例：

- `evaluator.power.ieee33_reactive_opt.default`
- `evaluator.power.ieee33_reactive_opt.robust`

### 5.3 Run

建议模式：

`run.<domain>.<problem_name>.<serial>`

示例：

- `run.power.ieee33_reactive_opt.0001`
- `run.power.ieee33_reactive_opt.0002`

其中 `serial` 应仅表示顺序，不承载语义。

### 5.4 Skill

建议模式：

`skill.<domain>.<capability_name>`

示例：

- `skill.power.baseline_solver`
- `skill.power.reactive_optimizer`
- `skill.power.voltage_deviation_estimator`

### 5.5 Cognition

建议模式：

`cognition.<domain>.<statement_key>`

示例：

- `cognition.power.weak_grid_voltage_support_rule`
- `cognition.power.loss_voltage_tradeoff_candidate`

### 5.6 Taste Assessment

建议模式：

`taste.<domain>.<problem_name>.<serial>`

示例：

- `taste.power.ieee33_reactive_opt.0001`

### 5.7 Evidence Bundle

建议模式：

`evidence.<domain>.<problem_name>.<serial>`

### 5.8 Report

建议模式：

`report.<domain>.<problem_name>.<report_kind>_<serial>`

示例：

- `report.power.ieee33_reactive_opt.note_0001`
- `report.power.ieee33_reactive_opt.memo_0001`

## 6. Version 规范

### 6.1 推荐形式

建议采用语义化版本形式：

`major.minor.patch`

示例：

- `0.1.0`
- `0.2.0`
- `1.0.0`

### 6.2 含义建议

- `major`
  表示不兼容变化

- `minor`
  表示向后兼容的结构或内容增强

- `patch`
  表示不改变核心语义的修订

### 6.3 注意事项

- `object_version` 不等于 `schema_version`
- `run` 对象也可以有版本，但其事实内容不应被无痕重写

## 7. 引用规范

### 7.1 基本引用

最基本引用至少指向 `object_id`。

例如：

```yaml
task_ref: "task.power.ieee33_reactive_opt"
```

### 7.2 版本化引用

当某个对象必须精确引用某一版时，应增加版本表达。

建议形式之一：

```yaml
skill_ref:
  object_id: "skill.power.reactive_optimizer"
  object_version: "0.2.0"
```

### 7.3 快照引用

当引用的是某次运行时实际使用的对象快照，应显式标明是运行快照，而不是最新对象。

例如：

```yaml
input_snapshot:
  task:
    object_id: "task.power.ieee33_reactive_opt"
    object_version: "0.1.0"
```

### 7.4 批量引用

多引用建议使用对象数组，而不是把多个 ID 挤进一个字符串。

### 7.5 反向引用

允许通过查询构建反向关系，但不建议每个对象都冗余写所有反向引用。

优先保留最关键的正向引用。

## 8. 文件路径与对象引用的关系

### 8.1 原则

文件路径是存储位置，不是对象身份。

### 8.2 推荐做法

对象内容中可包含：

- `file_ref`
- `artifact_ref`
- `implementation_ref`

但这些都只是对象的附属位置说明。

### 8.3 禁止做法

不要把路径字符串直接当作唯一对象 ID。

例如：

- 错误：`object_id: "tasks/task001/task.yaml"`

## 9. 命名冲突处理

如果同一问题域出现重名，应按以下方式解决：

1. 优先在 `scope` 层区分
2. 再在 `name` 层补充限定词
3. 不要用随机后缀掩盖命名不清的问题

## 10. 状态性对象的命名注意事项

`Run`、`Taste Assessment`、`Evidence Bundle` 这类对象具有明显时序性。

它们的命名应体现：

- 属于哪个问题域
- 属于哪次序列

但不应把成果判断直接编码进 ID。

例如不建议：

- `run.power.ieee33_reactive_opt.successful_final`

因为这会把可变判断混入稳定身份。

## 11. 最低执行要求

第一阶段至少要求：

1. 所有对象都有 `object_id`
2. 所有对象都有 `object_version`
3. 所有关键引用都不依赖路径字符串
4. `Run` 引用中能明确看出用了哪版 `Task` 与 `Evaluator`

## 12. 设计警戒线

以下情况说明命名与引用体系开始退化：

1. 同一对象在不同文件里出现多个 ID。
2. 使用文件名替代对象 ID。
3. 版本只写在标题里，不写在结构字段里。
4. 多对象引用被压成自然语言描述。
5. 把“成功”“失败”“创新”等判断写进稳定 ID。

若出现这些情况，应先修复命名与引用体系，再推进 schema 落地。
