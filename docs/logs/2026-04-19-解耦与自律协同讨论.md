# 2026-04-19 解耦与自律协同讨论

## 背景

在完成：

- 真实 `task001` 接入
- 候选技能 `weak_bus_shunt_optimizer`
- 结构化策略对照分析

之后，项目进入了一个新的基础问题讨论：

> 是否可以把整个自主科研框架设计成一个彻底解耦的系统？

这里的“彻底解耦”并不是否认前后逻辑关系，而是希望：

- 开发工作更独立
- 测试更可靠
- 部署更容易
- 单点失败不拖垮整体
- 项目在复杂度上升后仍能继续前进

## 讨论核心

讨论中明确提出了一个重要判断：

高耦合开发在科研和工程中都极易导致：

- 反复迭代
- 反复失败
- 局部修改牵动全局
- 开发节奏变慢
- 复杂度上升后进度饱和

相反，真正解耦的系统更容易：

- 成功
- 部署
- 可靠运行

## 新的目标表达

项目的下一层目标不应只是“模块化”，而应是：

> 将技能开发、认知提升、成效交付等能力设计成彼此独立可运行的应用。

这些应用之间：

- 不应存在强运行时耦合
- 不应因为一个应用未开发完成而阻塞其余应用
- 只应通过明确输入输出契约交互
- 当全部存在时，应形成一种“分散自律协同”的关系

## 这轮讨论的重要性

这轮讨论不是普通架构优化，而是在重新定义：

- 科研 Agent 的系统边界
- 多应用之间的协同方式
- orchestrator 的角色
- 技能、认知、成效之间应如何连接

也就是说，项目的核心问题正在从：

- 如何让一个 Agent 更强

转向：

- 如何让多个能力系统在低耦合条件下形成稳定科研生态

## 需要重点回答的问题

1. “彻底解耦”在这个项目里到底指什么
2. 哪些耦合必须保留，哪些耦合必须消除
3. 自律协同如何通过对象和协议实现
4. orchestrator 在这种系统里是中心控制器还是协调者
5. 技能、认知、成效是否应该变成独立应用

## 当前记录状态

本记录作为该轮讨论的起点。

后续应进一步沉淀：

- 解耦的分类
- 自律协同的原则
- 面向当前项目的应用划分
- 契约与运行机制设计

## 当前阶段判断

到当前阶段，已经形成以下判断：

### 判断 1

“彻底解耦”不意味着彼此毫无关系，而意味着：

- 语义上有关联
- 运行上不依赖
- 目标上协同
- 实现上自治

### 判断 2

应尽量消除：

- 运行时强耦合
- 开发强耦合
- 测试强耦合
- 共享可变状态耦合

### 判断 3

必须保留：

- 契约耦合
- 评价耦合
- 证据耦合

### 判断 4

项目长期不应演化为“大一统单体 Agent”，而应演化为：

- Task App
- Skill Lab App
- Evaluator App
- Cognition App
- Literature Alignment App
- Comparative Cognition Upgrade App
- Report App

所组成的分散自律协同系统。
