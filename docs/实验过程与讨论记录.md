# 实验过程与讨论记录

## 1. 文档目的

本文件用于系统记录本项目从概念形成、方法讨论、架构设计到实验推进过程中的关键讨论、技术选择、阶段结论和开放问题。

它不是简短进度汇报，而是面向后续反思与再研究的长期记录。

## 2. 为什么要记录

本项目本身就是一个实验性研究对象：

- 我们不仅在开发一个系统
- 也在研究 AI 如何辅助电力科研
- 同时还在提炼一种新的科研方法论

因此，过程本身就是材料。

很多真正重要的东西不会直接体现在代码里，而会体现在：

- 为什么当初这样设计
- 哪些路线被放弃
- 哪些判断后来被修正
- 哪些困难暴露了框架的真正边界

## 3. 项目起点

项目最初的关键问题不是“怎么把流程做完整”，而是“流程本身为什么经常不产生真正价值”。

由此提出了三个核心资产：

1. `技能`
2. `认知`
3. `成效`

对应的核心判断是：

- 科研不应以流程为中心
- 科研的主体常常是技能发展
- 认知是由技能应用与反思逐步升华出来的
- 成效是技能和认知提升后能够被外部验证的表现

这个判断奠定了整个项目的方向。

## 4. 第一次重要转向：从流程中心转向资产中心

项目早期讨论中最关键的认知之一是：

> 流程只是载体，流程的完美不等于创新的产生。

由此，项目不再追求“把科研流程自动化”，而是追求：

- 技能的持续积累
- 认知的持续沉淀
- 成效的独立验证

这直接决定了后续的系统设计必须围绕资产组织，而不是围绕步骤表演。

## 5. 第二次重要转向：将“品味”提升为系统内核

后续讨论中，一个更关键的判断被明确提出：

> 决定科研层次和影响力的核心，往往不是执行力，而是研究者的“品味”。

并进一步用四个层次加以表达：

1. 拓玉
2. 琢石
3. 雕木
4. 绘墨

这使项目不再只是“会做任务的 Agent”，而变成了：

> 一个必须学会判断成果质地、限制主张强度、避免自我包装的科研 Agent。

由此诞生了：

- `Taste Grader`
- `Claim Guard`
- `Report Gate`

也使得“品味”不再停留于哲学判断，而成为系统约束。

## 6. 第三次重要转向：技能网络与认知网络

项目随后进一步从“技能库/知识库”提升到“双网演进”：

- `技能网络`
- `认知网络`

这一步的核心意义是：

- 技能不再是扁平工具列表，而是可组合、可替代、可路径检索的资产图
- 认知不再是文档堆积，而是带证据、边界和冲突关系的语义图

这为后续的 GraphRAG、策略比较、认知升级都提供了理论基础。

## 7. 第四次重要转向：从“像研究生”到“研究科研人格”

在后续讨论中，项目目标被进一步提升：

> 我们不是只想做一个会完成任务的 Agent，而是想工程化一个优秀研究生的科研视角、逻辑、习惯与品味。

这使得项目拥有了三重身份：

1. 软件系统
2. 实验平台
3. 方法论装置

也使得“记录讨论与过程”本身成为项目核心，而不是附属工作。

## 9. 第一次真实闭环：task001 接入真实电力任务

为了避免框架长期停留在 demo 层，项目将 `task001` 接入到了真实 `pandapower case33bw`。

这个阶段最重要的意义不在于得到多好的结果，而在于：

- baseline/candidate/evaluator/report/writeback 整条链都进入了真实运行状态
- 成果不再是伪造指标
- taste 分级开始面对真实数据

这是项目从“方法论文档”进入“真实实验系统”的第一道门槛。

## 10. 对真实 task 的第一次判断修正

在接入真实 `task001` 后，一开始走的是：

- `ext_grid.vm_pu` 搜索

这条路线有价值，因为它证明了：

- 系统能在真实仿真上跑通
- evaluator 能独立比较 baseline 和 candidate

但随后一个更重要的判断出现了：

> 真实 execution 不等于真实技能。

也就是说，虽然 `ext_grid` 路线有效，但它还不够像一个“科研技能”。

这推动了项目进入下一次更重要的转向。

## 11. 第五次重要转向：从真实 execution 转向真实 skill evolution

后续讨论中，一个关键提醒被明确提出：

> 框架的核心不是把 demo 换成真实运行，而是让系统开始发展真实技能。

由此，项目不再优先追求：

- 扩工况
- 扩任务
- 扩流程

而是优先让系统研发一个更像研究方法的 candidate 技能。

## 12. 第二个真实 candidate 技能：weak_bus_shunt_optimizer

作为回应，项目实现了：

- `skill.power.weak_bus_shunt_optimizer`

它的核心思想是：

1. 识别弱电压节点
2. 搜索 shunt compensation 容量组合
3. 用统一 evaluator 比较指标

这一步的意义非常大，因为它标志着项目第一次真正从“真实算例”进入“真实技能研发”。

## 13. 当前阶段的关键发现

### 13.1 发现一：系统已经能生成候选技能

这说明框架不只是：

- 跑 baseline
- 跑评估
- 写报告

而是已经能把一个真实策略组织成一个候选技能节点。

### 13.2 发现二：真实技能不等于最优技能

`weak_bus_shunt_optimizer` 比 baseline 好，但当前仍不如 `ext-grid` 路线。

这暴露出一个重要认知：

> 更接近问题语义的技能，并不一定在第一轮就更强。

这类结论非常适合进入认知层，而不是被直接当成失败。

### 13.3 发现三：框架开始具备比较认知的基础

在进一步讨论中，又出现一个更高层问题：

> Agent 能做好技能开发，但能不能做好认知比较？

这推动项目新增了“比较分析作为框架能力”的路线。

## 14. 第六次重要转向：把“对照分析”做成框架能力

项目没有停留在人工读两个 run 再总结，而是新增了：

- `strategy_comparison` 对象
- `compare-runs` orchestrator 能力

这一步的关键意义在于：

- 不再是人替框架比较
- 而是框架自己生成结构化比较结果和比较认知

这是项目第一次触碰“认知比较自动化”的问题域。

## 15. 当前对“认知比较”的理解

到目前为止，项目已经形成一个比较明确的判断：

### 15.1 技能开发与成效验证

Agent 已经相对擅长：

- 写技能
- 跑评估
- 获取结果

### 15.2 认知比较

Agent 并不天然擅长。

认知比较至少要求：

1. 结构化记忆
2. 证据回链
3. 文献先验
4. 技能对照
5. 主张强度约束

因此，认知比较不能只是“再写一段总结”，而必须被架构化。

这也是项目最有研究价值的部分之一。

## 16. 当前开放问题

到这一阶段，项目暴露出的真正研究问题包括：

1. 一个 Agent 如何从“会执行”提升到“会比较认知”
2. 什么样的记忆结构最适合支撑认知比较
3. 文献对齐在何时进入框架，作用是什么
4. 品味约束在多轮比较中如何影响技能保留与认知晋升
5. 更接近问题语义的技能，何时才算真正“更高级”

## 19. 第七次重要转向：从“会比较结果”到“会比较认知”

在前一阶段，项目已经具备：

- 真实 task 接入
- 真实 candidate 技能
- 结构化策略对照分析

但随后一个更高层的问题被进一步明确提出：

> Agent 能否做好“认知比较”，而不仅仅是“结果比较”？

这推动项目进入下一阶段：

- 不再只比较哪个策略指标更好
- 而要比较哪种解释更可信、哪种认知更深、哪条路线更有研究价值

这一阶段的关键挑战不在于多写一个 compare 脚本，而在于：

- 如何让系统具备文献对齐能力
- 如何让系统比较“技能语义”和“认知层次”
- 如何在这一过程中继续受到成效和品味约束

## 20. 第八次重要转向：显式讨论“科研 Agent 的技术路线”

在进一步推进“文献对齐 + 比较认知升级”之前，项目又暴露出一个更基础的问题：

> 设计一个科研 Agent，究竟应采用什么技术路线？

候选路线被明确拆成三类：

1. 直接用 Python 脚本调用 LLM，手工组织上下文和多 Agent 行为
2. 使用 LangChain 或类似框架，按框架规范设计 Agent 及其交互
3. 采用成熟的 Agentic Coding 环境，再通过 harness 将其改造为科研专用 Agent

这一讨论本身非常重要，因为它不只是工程选型问题，而直接影响：

- 技能如何生成
- 认知如何沉淀
- 证据如何保留
- 框架如何演化
- 研究系统的可控性与可解释性

这一轮讨论应被视为项目的“基础路线决策讨论”，而不是普通实现细节。

## 21. 当前待展开的核心问题

在接下来的讨论中，需要集中回答以下问题：

1. 一个科研 Agent 的核心究竟是什么能力
2. 哪种技术路线最适合承载“技能 - 认知 - 成效”三要素
3. 哪种路线最利于记录、比较和升级认知
4. 哪种路线最利于后续接入文献对齐层
5. 是否应采用混合路线，而不是单一路线

## 22. 当前记录结论

到这一刻，项目的关键问题已经从：

- 如何把任务跑通

上升为：

- 如何设计一个真正适合“科研”的 Agent 技术底座

这说明项目正在从“工程搭建”进一步进入“方法论与系统路线选择”的核心区。

## 23. 第九次重要转向：从“模块化”走向“彻底解耦”

在进一步讨论技术路线后，又出现了一个更底层、更工程化但同样具有方法论意义的问题：

> 是否可以将整个自主科研框架设计成一个彻底解耦的系统？

这里的出发点非常明确：

- 高耦合开发在复杂项目中极易导致反复失败
- 当系统复杂度上升后，开发节奏会显著变慢
- 单点失效会阻塞整体演化

因此，项目开始不再只讨论：

- 用什么底座
- 用什么 Agent 环境

而开始讨论：

- 如何把技能开发、认知提升、成效交付都做成独立可运行的应用
- 如何让这些应用通过输入输出规范协同
- 如何在全部存在时形成“分散自律协同”

## 24. 当前阶段的新问题

这一轮讨论将项目进一步推向一个更高层的问题：

> 一个科研框架是否应该被设计成“多应用自律协同系统”，而不是单体 Agent 系统？

这个问题的意义在于：

- 它会重新定义 orchestrator 的角色
- 会重新定义技能、认知、成效的边界
- 会重新定义系统可靠性的来源

如果这一方向成立，那么项目下一阶段的核心就不只是“怎么做更多功能”，而是：

- 如何用契约而不是共享内部状态来连接系统
- 如何让每个能力应用可以独立开发、独立测试、独立失败
- 如何让协同变成一种协议，而不是耦合实现
