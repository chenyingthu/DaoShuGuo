# 实验过程与讨论记录

## 1. 文档目的

本文件用于系统记录本项目从概念形成、方法讨论、架构设计到实验推进过程中的关键讨论、技术选择、阶段结论和开放问题。

它不是简短进度汇报，而是面向后续反思与再研究的长期记录。

## 2. 为什么要记录

本项目本身就是一个实验性研究对象：

- 我们不仅在开发一个系统
- 也在研究 AI 如何辅助电力科研
- 同时还在提炼一种新的科研方法论

因此，过程本身就是材料。

很多真正重要的东西不会直接体现在代码里，而会体现在：

- 为什么当初这样设计
- 哪些路线被放弃
- 哪些判断后来被修正
- 哪些困难暴露了框架的真正边界

## 3. 项目起点

项目最初的关键问题不是“怎么把流程做完整”，而是“流程本身为什么经常不产生真正价值”。

由此提出了三个核心资产：

1. `技能`
2. `认知`
3. `成效`

对应的核心判断是：

- 科研不应以流程为中心
- 科研的主体常常是技能发展
- 认知是由技能应用与反思逐步升华出来的
- 成效是技能和认知提升后能够被外部验证的表现

这个判断奠定了整个项目的方向。

## 4. 第一次重要转向：从流程中心转向资产中心

项目早期讨论中最关键的认知之一是：

> 流程只是载体，流程的完美不等于创新的产生。

由此，项目不再追求“把科研流程自动化”，而是追求：

- 技能的持续积累
- 认知的持续沉淀
- 成效的独立验证

这直接决定了后续的系统设计必须围绕资产组织，而不是围绕步骤表演。

## 5. 第二次重要转向：将“品味”提升为系统内核

后续讨论中，一个更关键的判断被明确提出：

> 决定科研层次和影响力的核心，往往不是执行力，而是研究者的“品味”。

并进一步用四个层次加以表达：

1. 拓玉
2. 琢石
3. 雕木
4. 绘墨

这使项目不再只是“会做任务的 Agent”，而变成了：

> 一个必须学会判断成果质地、限制主张强度、避免自我包装的科研 Agent。

由此诞生了：

- `Taste Grader`
- `Claim Guard`
- `Report Gate`

也使得“品味”不再停留于哲学判断，而成为系统约束。

## 6. 第三次重要转向：技能网络与认知网络

项目随后进一步从“技能库/知识库”提升到“双网演进”：

- `技能网络`
- `认知网络`

这一步的核心意义是：

- 技能不再是扁平工具列表，而是可组合、可替代、可路径检索的资产图
- 认知不再是文档堆积，而是带证据、边界和冲突关系的语义图

这为后续的 GraphRAG、策略比较、认知升级都提供了理论基础。

## 7. 第四次重要转向：从“像研究生”到“研究科研人格”

在后续讨论中，项目目标被进一步提升：

> 我们不是只想做一个会完成任务的 Agent，而是想工程化一个优秀研究生的科研视角、逻辑、习惯与品味。

这使得项目拥有了三重身份：

1. 软件系统
2. 实验平台
3. 方法论装置

也使得“记录讨论与过程”本身成为项目核心，而不是附属工作。

## 11. 第五次重要转向：从真实 execution 转向真实 skill evolution

> 框架的核心不是把 demo 换成真实运行，而是让系统开始发展真实技能。

由此，项目不再优先追求：

- 扩工况
- 扩任务

而是优先让系统研发一个更像研究方法的 candidate 技能。

## 14. 第六次重要转向：底层 Agent harness 从 Codex 转向 Pi

随着项目向真实 Agent 回路推进，一个越来越清晰的事实出现了：

> 仅靠当前对 Codex/Claude Code 一类成熟 coding agent 的 harness，很难稳定定义我们真正想要的科研 Agent 行为。

因此，项目进行了重要底层转向：

- 不再把 Codex 当成最终科研 Agent runtime
- 转而把 `Pi` 作为更可控、更可 harness 的底层 Agent 环境

这不是主线偏离，而是对主线的必要支撑。因为如果底层 Agent 无法被稳定定义和驱动，后续“技能-认知-成效”闭环就只能停留在规则层或伪 Agent 层。

## 15. Pi 路线的一个关键结论：Python 保持 domain runtime，Pi 负责 agent loop

在 Pi 可行性研究和随后的 task003/task004 工作中，项目逐步明确了一个重要技术路线：

- `Pi` 负责 agent loop、工具调用、durable loop 记忆和回路状态
- Python 继续负责电力科研任务本体、evaluator、schema、writeback 和 report 资产

这意味着项目没有改成“全都交给 Pi”，而是形成了一个更合理的分工：

> Agent 负责研究行为；确定性系统负责运行、验证、约束和记忆。

对应关键产物包括：

这次运行证明了三件事：

1. Pi 已不只是能跑 task003，也能真实支撑 task004

3. task004 适合作为 `认知 + 成效` 层的测试任务，而不仅是技能对比任务

## 17. task004 这轮测试的真正价值，不是得到更优 candidate，而是得到高质量 failure-boundary 样本

`run_0005` 的结论并不是“candidate 成功改进了承载力边界”。

恰恰相反，它给出的是一个受控失败：

- candidate 未提高当前扫描包络下的 hosting-capacity boundary
- run 被正确记为 `failed_experiment`
- 同时系统仍然成功写出了：
  - boundary judgment
  - claim ceiling
  - effectiveness status
  - iteration review

这说明项目开始具备一种非常重要的能力：

> 不把失败样本浪费掉，而是把失败样本转化为认知与成效层的真实材料。

这与项目最初强调的“失败观”高度一致，也说明 task004 的设计方向是正确的。

## 18. 当前仍需保持清醒的地方

虽然 task004 的 Pi 最小闭环已经真实跑通，但仍有几个事实需要明确记录：

1. 当前完成的是 `light slice`，不是更重的 multi-iteration cognition loop
2. Pi CLI 在 artifacts 已经落盘后，有时退出较慢
3. 这轮 task004 证明的是：
   - provider 可用
   - loop 可用
   - 边界与成效记录可用
   但还没有证明：
   - task004 已具备 paper-grade deliverable 生产力
   - cognition layer 已达到高水平研究判断能力

换句话说，这是一轮非常重要的“打通性证明”，但还不是终局证明。

## 36. 新阶段：把“认知总结”改造成“认知约束技能”

在 task003~task005 的技能层、认知层、成效层以及 LLM 认知层建立后，一个新的核心问题被明确提出：

> 如果认知不能显式改写下一轮 skill 的搜索空间、评估空间和任务空间，那么所谓闭环仍然只是形式主义。

这一步是本项目的重要反思：

- 之前系统已经能生成比较、升级、文献对齐、解释对齐
- 也已经能让真实 Codex agent 参与 cognition workflow
- 但这些结果仍然主要停留在“分析”和“评价”层
- 还没有正式进入“重写下一轮技能工作边界”的层

因此，项目新增了一个专门的框架层：

- `cognition_event`
- `cognition_to_skill_update`
- `skill_iteration_plan`
- `loop_review`

这四类对象的目标非常清晰：

- `cognition_event`：把值得上升为认知处理的现象显式对象化
- `cognition_to_skill_update`：把认知转译为下一轮技能约束
- `skill_iteration_plan`：把下一轮技能探索改写为受约束计划
- `loop_review`：检查这一轮 loop 是否真的缩小了盲搜空间

## 37. 为什么这一步是必要的

这一步不是简单增加更多对象，而是在回应一个更深的问题：

> Agent 为什么要被纳入这个系统？如果技能、认知、成效只是规则驱动和文档驱动，那么它并不真正“像研究生”，也不真正具有科研闭环能力。

此前用户明确指出：

- 规则不能产生超出规则本身的知识和认知
- 如果没有 LLM-based agent 真正参与 cognition 和 result work，系统并不智能，也不自主

这个提醒非常重要。

因此，项目在 AGENTS.md 中明确写下了一条经验教训：

- rules / schemas 是 guardrail，不是 cognition 本身
- 真实 cognition worker 必须由 LLM agent 承担

但与此同时，另一个工程事实也必须被承认：

- 如果没有对象层和控制层
- 即使 LLM cognition worker 做出高质量判断
- 这些判断也很容易散落为文本，不会自动变成下一轮技能工作约束

因此，这一轮实现的意义不是替代 agent，而是为 agent cognition 提供一个正式的控制接口。

## 38. 本轮闭环实现的技术路线

本轮没有直接去做一个重型自治控制平台，而是选择了更稳妥的路线：

1. 先把闭环中的关键流动对象对象化
2. 再把 task003 / task004 / task005 的现有真实分析资产接成最小 controller
3. 让 controller 自动输出下一轮技能约束与计划
4. 最后把它纳入 schema / verifier / orchestrator / integration checks

- `analysis/loop/task003/*`

- `analysis/loop/task005/*`

## 39. 这轮实现到底完成了什么

这轮实现已经把以下事情正式做成框架能力：

### 39.1 事件提取

基于现有真实资产，系统能够为不同 task 生成不同类型的 `cognition_event`：

- task003: `metric_semantic_divergence`
- task004: `claim_overreach_detected`
- task005: `skill_mismatch_detected`

### 39.2 认知到技能的转译

系统能够基于现有认知资产，生成 `cognition_to_skill_update`，明确：

- 哪些 skill family 应继续
- 哪些 skill family 应冻结或阻断
- evaluator 下一轮必须修正什么
- task 下一轮必须补哪些定义与实验

### 39.3 下一轮技能计划

系统能够生成 `skill_iteration_plan`，把下一轮 skill work 从“盲试”改写成“受约束探索”。

例如：

- task003 不应退回 weak-shunt 替代主线，而应在新能源控制家族内部做协同扩展
- task004 不应继续把单点运行结果当作承载力边界代理，而应补边界扫描与多场景对照
- task005 不应让 steady-state skill 混入恢复主线，而应围绕事件驱动恢复和 fault topology 做扩展

### 39.4 闭环审视

系统能够生成 `loop_review`，显式判断这一轮 loop 是否真的：

- 缩小了搜索空间
- 改善了 failure 解释
- 推动了 evaluator refinement
- 收紧了 claim boundary

## 40. 这轮实现没有完成什么

这一点同样重要，必须明确写下。

当前实现的 `Cognition-to-Skill Controller` 仍然是：

> bootstrap controller

它的特点是：

- 它基于已有 task003 / task004 / task005 的分析资产工作
- 它能正式输出下一轮技能约束
- 它已接入验证链路
- 但它还不是由 LLM cognition workflow 直接主导生成

也就是说：

- 当前闭环层已经从“讨论”变成“框架能力”
- 但它还不是最终的 agent-native autonomous loop

真正的下一阶段应该是：

- 让 LLM cognition worker 读取 `cognition_event`
- 输出更高质量的 `cognition_to_skill_update`
- 再由技能开发工作流读取这些 update，触发真实 skill iteration

## 41. 一个关键经验：不要把“有了对象”误判为“实现了自主认知”

这是本轮最重要的反思之一。

新增对象层非常必要，但它本身不等于系统已经拥有自主研究能力。

真正的自主研究能力至少还需要：

- LLM cognition worker 的更强 prompt / workflow / memory 设计
- 它们与 loop controller 的正式耦合
- loop 输出对真实 skill 开发边界的持续重写
- 再由真实 task 验证这一闭环是否不断把系统推向更高水平

因此，这一轮的正确评价不是：

- “已经实现了完整的自主演化”

而是：

- “已经把技能-认知闭环中最关键的控制接口正式落地，为 agent-native 闭环提供了真实承载层。”

## 42. 第六次重要转向：底层 Agent Harness 问题

在继续尝试真实 `skill agent <-> cognition agent` 多轮闭环时，一个更底层的问题被明确暴露：

> 如果底层 coding agent runtime 本身不适合被科研框架精确 harness，那么上层设计再完整，也很难形成稳定自主循环。

此前我们尝试用 Codex 做真实多轮 agentic loop，已经证明：

- 单轮 cognition agent 可以工作
- bounded skill-agent request 可以产生真实 skill 变体
- 但多轮组合时，会不断遇到 session、sandbox、timeout、partial artifact、resume、子进程残留等执行层问题
- 更重要的是，成熟 coding-agent 产品自身已有很强的产品级架构和约束，我们必须与其设计搏斗

这不是某个实现细节失败，而是底层 harness 选择问题。

因此，项目转向研究 Pi：

- `badlogic/pi-mono/packages/coding-agent`
- `davebcn87/pi-autoresearch`

这个转向表面上看像偏离主线，但实际是在修主线地基。

### 43.3 对 DaoShuGuo 的意义

Pi 的核心优势不是“模型更强”，而是：

> 它是一个很薄、可扩展、可嵌入、可包化的 coding-agent harness。

它允许我们把 DaoShuGuo 做成：

- extension
- skill
- prompt templates
- package

## 23. 第九次重要转向：从“模块化”走向“彻底解耦”

在进一步讨论技术路线后，又出现了一个更底层、更工程化但同样具有方法论意义的问题：

这里的出发点非常明确：

- 高耦合开发在复杂项目中极易导致反复失败

- 如何让这些应用通过输入输出规范协同
- 如何在全部存在时形成“分散自律协同”

## 24. 当前阶段的新问题

- 如何用契约而不是共享内部状态来连接系统
- 如何让每个能力应用可以独立开发、独立测试、独立失败
- 如何让协同变成一种协议，而不是耦合实现

因此，框架要求从此变成：

- 成功时形成 success cognition
- 失败时形成 failure cognition
- 二者都必须经过 taste 约束
- 二者都必须进入 report/writeback 体系

1. 验证 evaluator 确实会判失败
2. 验证 cognition 会落到 `failure`

4. 验证 report 会被压到 `discussion_memo`

这说明系统已经具备了：

在主线任务已经相对完整之后，项目没有继续盲目扩任务，而是回过头来吸收了一部分 `ResearchGraphBuilder` 中更成熟的验证基础设施思想。

这次吸收没有照搬整套项目，而是只取了三类最契合当前项目的能力：

1. `preflight / light probe`
2. `experiment index`
3. `diagnosis memory`

## 69. 当前吸收结果

### 69.1 preflight / light probe

新增：

- `scripts/run_preflight_checks.py`
- `scripts/run_light_probe.py`

作用：

- 在正式执行前快速判断当前项目是否处于 `ready / blocked` 状态
- 降低后续 task 进入执行前的无谓失败概率

### 69.2 experiment index

新增：

- `scripts/build_experiment_index.py`

输出：

- `analysis/experiment_index.json`
- `analysis/experiment_index.md`

作用：

- 把 task002/003/004 的 success/failure/compare/upgrade 资产组织成统一索引
- 让实验主线变得可回看、可比较、可导航

### 69.3 diagnosis memory

新增：

- `scripts/update_diagnosis_memory.py`
- `memory/diagnosis_memory.jsonl`

作用：

- 将已有 failure cognition 回填为可检索诊断记忆
- 让 failure taxonomy 不只存在于单个认知对象里，而进入更长期的记忆层

## 70. 这一步的意义

这一轮吸收工作说明：

> 项目开始从“能做研究任务”进一步走向“能对自己的执行与失败进行工程化管理”。

也就是说，当前系统不再只是：

- 会定义 task
- 会开发 skill
- 会形成 cognition

而开始具备：

- 执行前预检
- 实验资产索引
- 失败诊断记忆

这三者都是后续做更大规模 task005/006 时非常关键的“框架韧性”能力。
