# 实验过程与讨论记录

## 1. 文档目的

本文件用于系统记录本项目从概念形成、方法讨论、架构设计到实验推进过程中的关键讨论、技术选择、阶段结论和开放问题。

它不是简短进度汇报，而是面向后续反思与再研究的长期记录。

## 2. 为什么要记录

本项目本身就是一个实验性研究对象：

- 我们不仅在开发一个系统
- 也在研究 AI 如何辅助电力科研
- 同时还在提炼一种新的科研方法论

因此，过程本身就是材料。

很多真正重要的东西不会直接体现在代码里，而会体现在：

- 为什么当初这样设计
- 哪些路线被放弃
- 哪些判断后来被修正
- 哪些困难暴露了框架的真正边界

## 3. 项目起点

项目最初的关键问题不是“怎么把流程做完整”，而是“流程本身为什么经常不产生真正价值”。

由此提出了三个核心资产：

1. `技能`
2. `认知`
3. `成效`

对应的核心判断是：

- 科研不应以流程为中心
- 科研的主体常常是技能发展
- 认知是由技能应用与反思逐步升华出来的
- 成效是技能和认知提升后能够被外部验证的表现

这个判断奠定了整个项目的方向。

## 4. 第一次重要转向：从流程中心转向资产中心

项目早期讨论中最关键的认知之一是：

> 流程只是载体，流程的完美不等于创新的产生。

由此，项目不再追求“把科研流程自动化”，而是追求：

- 技能的持续积累
- 认知的持续沉淀
- 成效的独立验证

这直接决定了后续的系统设计必须围绕资产组织，而不是围绕步骤表演。

## 5. 第二次重要转向：将“品味”提升为系统内核

后续讨论中，一个更关键的判断被明确提出：

> 决定科研层次和影响力的核心，往往不是执行力，而是研究者的“品味”。

并进一步用四个层次加以表达：

1. 拓玉
2. 琢石
3. 雕木
4. 绘墨

这使项目不再只是“会做任务的 Agent”，而变成了：

> 一个必须学会判断成果质地、限制主张强度、避免自我包装的科研 Agent。

由此诞生了：

- `Taste Grader`
- `Claim Guard`
- `Report Gate`

也使得“品味”不再停留于哲学判断，而成为系统约束。

## 6. 第三次重要转向：技能网络与认知网络

项目随后进一步从“技能库/知识库”提升到“双网演进”：

- `技能网络`
- `认知网络`

这一步的核心意义是：

- 技能不再是扁平工具列表，而是可组合、可替代、可路径检索的资产图
- 认知不再是文档堆积，而是带证据、边界和冲突关系的语义图

这为后续的 GraphRAG、策略比较、认知升级都提供了理论基础。

## 7. 第四次重要转向：从“像研究生”到“研究科研人格”

在后续讨论中，项目目标被进一步提升：

> 我们不是只想做一个会完成任务的 Agent，而是想工程化一个优秀研究生的科研视角、逻辑、习惯与品味。

这使得项目拥有了三重身份：

1. 软件系统
2. 实验平台
3. 方法论装置

也使得“记录讨论与过程”本身成为项目核心，而不是附属工作。

## 11. 第五次重要转向：从真实 execution 转向真实 skill evolution

> 框架的核心不是把 demo 换成真实运行，而是让系统开始发展真实技能。

由此，项目不再优先追求：

- 扩工况
- 扩任务

而是优先让系统研发一个更像研究方法的 candidate 技能。

## 14. 第六次重要转向：底层 Agent harness 从 Codex 转向 Pi

随着项目向真实 Agent 回路推进，一个越来越清晰的事实出现了：

> 仅靠当前对 Codex/Claude Code 一类成熟 coding agent 的 harness，很难稳定定义我们真正想要的科研 Agent 行为。

因此，项目进行了重要底层转向：

- 不再把 Codex 当成最终科研 Agent runtime
- 转而把 `Pi` 作为更可控、更可 harness 的底层 Agent 环境

这不是主线偏离，而是对主线的必要支撑。因为如果底层 Agent 无法被稳定定义和驱动，后续“技能-认知-成效”闭环就只能停留在规则层或伪 Agent 层。

## 15. Pi 路线的一个关键结论：Python 保持 domain runtime，Pi 负责 agent loop

在 Pi 可行性研究和随后的 task003/task004 工作中，项目逐步明确了一个重要技术路线：

- `Pi` 负责 agent loop、工具调用、durable loop 记忆和回路状态
- Python 继续负责电力科研任务本体、evaluator、schema、writeback 和 report 资产

这意味着项目没有改成“全都交给 Pi”，而是形成了一个更合理的分工：

> Agent 负责研究行为；确定性系统负责运行、验证、约束和记忆。

对应关键产物包括：

这次运行证明了三件事：

1. Pi 已不只是能跑 task003，也能真实支撑 task004

3. task004 适合作为 `认知 + 成效` 层的测试任务，而不仅是技能对比任务

## 17. task004 这轮测试的真正价值，不是得到更优 candidate，而是得到高质量 failure-boundary 样本

`run_0005` 的结论并不是“candidate 成功改进了承载力边界”。

恰恰相反，它给出的是一个受控失败：

- candidate 未提高当前扫描包络下的 hosting-capacity boundary
- run 被正确记为 `failed_experiment`
- 同时系统仍然成功写出了：
  - boundary judgment
  - claim ceiling
  - effectiveness status
  - iteration review

这说明项目开始具备一种非常重要的能力：

> 不把失败样本浪费掉，而是把失败样本转化为认知与成效层的真实材料。

这与项目最初强调的“失败观”高度一致，也说明 task004 的设计方向是正确的。

## 18. 当前仍需保持清醒的地方

虽然 task004 的 Pi 最小闭环已经真实跑通，但仍有几个事实需要明确记录：

1. 当前完成的是 `light slice`，不是更重的 multi-iteration cognition loop
2. Pi CLI 在 artifacts 已经落盘后，有时退出较慢
3. 这轮 task004 证明的是：
   - provider 可用
   - loop 可用
   - 边界与成效记录可用
   但还没有证明：
   - task004 已具备 paper-grade deliverable 生产力
   - cognition layer 已达到高水平研究判断能力

换句话说，这是一轮非常重要的“打通性证明”，但还不是终局证明。

## 36. 新阶段：把“认知总结”改造成“认知约束技能”

在 task003~task005 的技能层、认知层、成效层以及 LLM 认知层建立后，一个新的核心问题被明确提出：

> 如果认知不能显式改写下一轮 skill 的搜索空间、评估空间和任务空间，那么所谓闭环仍然只是形式主义。

这一步是本项目的重要反思：

- 之前系统已经能生成比较、升级、文献对齐、解释对齐
- 也已经能让真实 Codex agent 参与 cognition workflow
- 但这些结果仍然主要停留在“分析”和“评价”层
- 还没有正式进入“重写下一轮技能工作边界”的层

因此，项目新增了一个专门的框架层：

- `cognition_event`
- `cognition_to_skill_update`
- `skill_iteration_plan`
- `loop_review`

这四类对象的目标非常清晰：

- `cognition_event`：把值得上升为认知处理的现象显式对象化
- `cognition_to_skill_update`：把认知转译为下一轮技能约束
- `skill_iteration_plan`：把下一轮技能探索改写为受约束计划
- `loop_review`：检查这一轮 loop 是否真的缩小了盲搜空间

## 37. 为什么这一步是必要的

这一步不是简单增加更多对象，而是在回应一个更深的问题：

> Agent 为什么要被纳入这个系统？如果技能、认知、成效只是规则驱动和文档驱动，那么它并不真正“像研究生”，也不真正具有科研闭环能力。

此前用户明确指出：

- 规则不能产生超出规则本身的知识和认知
- 如果没有 LLM-based agent 真正参与 cognition 和 result work，系统并不智能，也不自主

这个提醒非常重要。

因此，项目在 AGENTS.md 中明确写下了一条经验教训：

- rules / schemas 是 guardrail，不是 cognition 本身
- 真实 cognition worker 必须由 LLM agent 承担

但与此同时，另一个工程事实也必须被承认：

- 如果没有对象层和控制层
- 即使 LLM cognition worker 做出高质量判断
- 这些判断也很容易散落为文本，不会自动变成下一轮技能工作约束

因此，这一轮实现的意义不是替代 agent，而是为 agent cognition 提供一个正式的控制接口。

## 38. 本轮闭环实现的技术路线

本轮没有直接去做一个重型自治控制平台，而是选择了更稳妥的路线：

1. 先把闭环中的关键流动对象对象化
2. 再把 task003 / task004 / task005 的现有真实分析资产接成最小 controller
3. 让 controller 自动输出下一轮技能约束与计划
4. 最后把它纳入 schema / verifier / orchestrator / integration checks

- `analysis/loop/task003/*`

- `analysis/loop/task005/*`

## 39. 这轮实现到底完成了什么

这轮实现已经把以下事情正式做成框架能力：

### 39.1 事件提取

基于现有真实资产，系统能够为不同 task 生成不同类型的 `cognition_event`：

- task003: `metric_semantic_divergence`
- task004: `claim_overreach_detected`
- task005: `skill_mismatch_detected`

### 39.2 认知到技能的转译

系统能够基于现有认知资产，生成 `cognition_to_skill_update`，明确：

- 哪些 skill family 应继续
- 哪些 skill family 应冻结或阻断
- evaluator 下一轮必须修正什么
- task 下一轮必须补哪些定义与实验

### 39.3 下一轮技能计划

系统能够生成 `skill_iteration_plan`，把下一轮 skill work 从“盲试”改写成“受约束探索”。

例如：

- task003 不应退回 weak-shunt 替代主线，而应在新能源控制家族内部做协同扩展
- task004 不应继续把单点运行结果当作承载力边界代理，而应补边界扫描与多场景对照
- task005 不应让 steady-state skill 混入恢复主线，而应围绕事件驱动恢复和 fault topology 做扩展

### 39.4 闭环审视

系统能够生成 `loop_review`，显式判断这一轮 loop 是否真的：

- 缩小了搜索空间
- 改善了 failure 解释
- 推动了 evaluator refinement
- 收紧了 claim boundary

## 40. 这轮实现没有完成什么

这一点同样重要，必须明确写下。

当前实现的 `Cognition-to-Skill Controller` 仍然是：

> bootstrap controller

它的特点是：

- 它基于已有 task003 / task004 / task005 的分析资产工作
- 它能正式输出下一轮技能约束
- 它已接入验证链路
- 但它还不是由 LLM cognition workflow 直接主导生成

也就是说：

- 当前闭环层已经从“讨论”变成“框架能力”
- 但它还不是最终的 agent-native autonomous loop

真正的下一阶段应该是：

- 让 LLM cognition worker 读取 `cognition_event`
- 输出更高质量的 `cognition_to_skill_update`
- 再由技能开发工作流读取这些 update，触发真实 skill iteration

## 41. 一个关键经验：不要把“有了对象”误判为“实现了自主认知”

这是本轮最重要的反思之一。

新增对象层非常必要，但它本身不等于系统已经拥有自主研究能力。

真正的自主研究能力至少还需要：

- LLM cognition worker 的更强 prompt / workflow / memory 设计
- 它们与 loop controller 的正式耦合
- loop 输出对真实 skill 开发边界的持续重写
- 再由真实 task 验证这一闭环是否不断把系统推向更高水平

因此，这一轮的正确评价不是：

- “已经实现了完整的自主演化”

而是：

- “已经把技能-认知闭环中最关键的控制接口正式落地，为 agent-native 闭环提供了真实承载层。”

## 42. 第六次重要转向：底层 Agent Harness 问题

在继续尝试真实 `skill agent <-> cognition agent` 多轮闭环时，一个更底层的问题被明确暴露：

> 如果底层 coding agent runtime 本身不适合被科研框架精确 harness，那么上层设计再完整，也很难形成稳定自主循环。

此前我们尝试用 Codex 做真实多轮 agentic loop，已经证明：

- 单轮 cognition agent 可以工作
- bounded skill-agent request 可以产生真实 skill 变体
- 但多轮组合时，会不断遇到 session、sandbox、timeout、partial artifact、resume、子进程残留等执行层问题
- 更重要的是，成熟 coding-agent 产品自身已有很强的产品级架构和约束，我们必须与其设计搏斗

这不是某个实现细节失败，而是底层 harness 选择问题。

因此，项目转向研究 Pi：

- `badlogic/pi-mono/packages/coding-agent`
- `davebcn87/pi-autoresearch`

这个转向表面上看像偏离主线，但实际是在修主线地基。

### 43.3 对 DaoShuGuo 的意义

Pi 的核心优势不是“模型更强”，而是：

> 它是一个很薄、可扩展、可嵌入、可包化的 coding-agent harness。

它允许我们把 DaoShuGuo 做成：

- extension
- skill
- prompt templates
- package

## 23. 第九次重要转向：从“模块化”走向“彻底解耦”

在进一步讨论技术路线后，又出现了一个更底层、更工程化但同样具有方法论意义的问题：

这里的出发点非常明确：

- 高耦合开发在复杂项目中极易导致反复失败

- 如何让这些应用通过输入输出规范协同
- 如何在全部存在时形成“分散自律协同”

## 24. 当前阶段的新问题

- 如何用契约而不是共享内部状态来连接系统
- 如何让每个能力应用可以独立开发、独立测试、独立失败
- 如何让协同变成一种协议，而不是耦合实现

因此，框架要求从此变成：

- 成功时形成 success cognition
- 失败时形成 failure cognition
- 二者都必须经过 taste 约束
- 二者都必须进入 report/writeback 体系

1. 验证 evaluator 确实会判失败
2. 验证 cognition 会落到 `failure`

4. 验证 report 会被压到 `discussion_memo`

这说明系统已经具备了：

## 90. 技能定义的关键修正：技能不是算法，而是方法、流程和标准

在 task003 iter02 被 review gate 判定为 `approved_with_ablation_required` 后，项目进一步讨论了一个更根本的问题：

> 当前指标改善是否真的代表技能提升？

这次讨论形成了一个关键修正：

技能不是单个算法文件，也不是某次 candidate 的执行结果。完整技能至少包含三类要素：

1. 方法：加工信息和数据的函数、算法或具体逻辑。
2. 流程：多个方法和数据处理逻辑的组织方式，包括分支、并行、条件和循环。
3. 标准：衡量工作质量的方法，包括性能指标、指标计算和综合评价。

因此，技能改进也必须区分两类：

1. 技能使用改善：通过改变边界条件、参数、搜索空间、调用方式或资源投入，使评价结果变好。
2. 技能结构提升：方法、流程或标准本身变得更准确、高效、可扩展、可泛化、可解释、可复用或更有比较优势。

task003 iter02 的改善属于第一类。它证明了更大的 inverter-Q 搜索空间在当前 evaluator 和单代表工况下产生了更好指标，但尚未证明方法、流程或标准发生结构性提升。

这条认知已经写入：

- `AGENTS.md`
- `docs/research-plan-execute-protocol.md`
- `docs/合格科研研究生Agent规范.md`
- `docs/工作原则与研发方法.md`
- `scripts/run_research_review_gate.py`

## 91. Loopy research flow 的目标修正

此前的循环可表述为：

`技能开发 -> 成效评估 -> 认知提升 -> 技能开发`

这条链路如果缺少结构性约束，很容易退化为：

- 反复调参数
- 扩大搜索空间
- 适配单个 task
- 通过更大代价换取局部指标改善

因此，本项目对 loop 的目标做了修正：

> 循环不是为了不断找到更好的 task-specific 参数，而是为了把局部 skill-use 观察转化为方法、流程和标准层面的结构性问题。

如果多轮循环只能产生第一类改善，不能沉淀第二类结构性提升，则该循环应被标记为：

`local_skill_use_optimization`

不得宣称为：

`agentic_skill_evolution_verified`

## 92. 为什么需要 learning worker

进一步讨论发现，认知 worker 不应凭空“想出”结构性提升。一个合格研究生的进步往往来自：

- 发现自己不懂什么
- 查文献
- 比较已有方法
- 学习成熟算法结构
- 再回到自己的问题中判断

因此，项目引入了 `learning_worker` 或 `literature_worker` 的角色。

该角色不是为了增加复杂多智能体，而是为了把外部学习材料供给对象化、可审计化。

角色分工如下：

1. cognition worker 提出 `learning_need`
2. learning worker 产出 `learning_context_pack`
3. cognition worker 阅读资料并形成 `skill_structure_diagnosis`
4. skill worker 根据 `structural_skill_change_request` 实施结构性尝试

这避免了一个危险路径：

> cognition worker 隐式使用模型内部知识或幻觉资料，然后把它包装成认知升级。

这带来一个必须正视的质疑：

如果突然给出 task007、task008，系统能否直接接入？

如果每个新 task 都需要重新写一批脚本、schema、verifier、adapter，那么这个系统就不是通用自主科研框架，而是“带文档的任务定制开发”。

- `--task task003 --iteration 2` 专用 replay
- 针对某个 task 单独生成的 context pack
- 针对某个 task 单独写的 verifier
- 针对某个 task 单独编码的 metrics 解释

这些都有研究价值，但只能称为 fixture 或 replay experiment。

## 102. 新的硬目标：Generic Task Onboarding

下一阶段的核心目标变为：

统一 onboarding 层至少要检查：

1. task package 是否完整

3. evaluator 是否存在且可绑定

这个问题说明：

1. Agent 具备语义判断能力不等于 artifact contract 自动可靠。
2. 自主科研框架必须把 LLM worker 和 deterministic controller 分开。
3. controller 的职责是验证、重试、约束和持久化，而不是替 worker 下判断。

仍然不能声称的事情：

1. 还不能声称 Level 4 backend-robust agentic full loop，因为 Codex/OMX full-loop backend dispatch 未实现。
2. 还不能声称 Level 5 research-quality autonomous cognition，因为当前是 fixture-level validation。
3. 还不能声称跨后端语义一致性，因为 Codex/OMX 后端没有同矩阵运行结果。

本轮最重要的设计收获：

通用自主科研框架的核心不是“写一个更长的脚本”，而是建立稳定的四层分离：

1. task package / adapter 只描述任务绑定。
2. worker backend 负责产生 skill/effectiveness/cognition 判断。
3. deterministic controller 负责对象写入、契约验证、证据回链和路由。
4. verifier/report 负责证明什么成立、什么没有成立。

这使得后续 task007、task008、task009 等新任务不需要专用框架代码，也能被同一机制接入、执行或阻断。

## 110. 后端泛化修正：从 Pi 专用 worker 回到统一 backend dispatch

在通用完整闭环验证之后，我们发现一个架构问题：

虽然系统已经有统一入口 `scripts/run_generic_loop_engine.py`，但 Pi 后端最初是通过：

```bash
--backend pi_gpt55 --worker-module <old Pi-specific worker module>
```

接入的。

这会造成一个错误倾向：

1. backend 切换看起来依赖替换 worker module。
2. Pi/Codex/未来 backend 容易各自长出一套专用 worker。
3. 系统再次滑向特异化实现，而不是真正的 generic 设计。

因此，本轮进行了架构收敛：

1. 新增 `configs/agent_runtimes/registry.yaml` 作为统一 agent runtime registry。
2. 新增 `scripts/backend_registry.py` 作为唯一 backend 解析层。
3. 新增 `scripts/llm_full_loop_workers.py` 作为通用 LLM worker runtime。
4. `scripts/run_generic_loop_engine.py` 默认根据 `--backend` 查 registry，自动获得 worker module、runner、provider、model、thinking mode、raw output root。
5. `--worker-module` 保留，但只作为 debug override，不再是正式验证路径。

现在正式调用方式为：

```bash
python scripts/run_generic_loop_engine.py \
  --task-adapter adapters/task006_near_neighbor.yaml \
  --backend pi_gpt55 \
  --run-intent full_loop_validation
```

而不是手动指定 Pi worker module。

这次修正确认了一个关键原则：

后端差异应该由配置和 runner adapter 表达，而不是由任务、adapter 或 controller 中的特化逻辑表达。

当前 registry 中的 backend 状态：

1. `deterministic`: active，使用 Python deterministic worker。
2. `pi_gpt55`: active，使用通用 LLM worker runtime + Pi runner + Pi agent profile。
3. `codex_omx`: blocked，已经在 registry 中建模，但 framework-callable runner adapter 还没有实现。

重新验证结果：

1. `task006_near_neighbor` deterministic 统一入口通过。
2. `task006_near_neighbor` Pi GPT-5.5 统一入口通过。
3. `task008_bad_candidate` Pi GPT-5.5 统一入口通过。
4. `task009_evaluator_gap` Pi GPT-5.5 统一入口通过。
5. `verify_generic_full_loop.py --all` 通过。
6. `compare_loop_backends.py --all` 通过，且后端信息来自 registry。
7. `validate_schemas.py --artifacts generic-full-loop-validation` 通过。

这次修正的意义是：

从“Pi 可以跑通”升级为“后端切换开始进入统一配置机制”。这比多跑几个任务更重要，因为它修复了框架泛化方向上的结构性漏洞。

## 112. 多 task × 多 Pi runtime 矩阵验证

为了回应“通用框架不能只针对单个 task 或单个模型成立”的要求，本轮把验证从单一 Pi GPT-5.5 后端扩展为多 task、多 runtime 的组合矩阵。

矩阵配置：

```bash
python scripts/run_agent_runtime_matrix.py \
  --tasks task006_near_neighbor task008_bad_candidate task009_evaluator_gap task010_literature_required task011_portfolio_stop \
  --runtimes pi_gpt55 pi_baidu_glm5 pi_baidu_kimi_k25 pi_baidu_minimax_m25 \
  --max-workers 3 \
  --timeout 240
```

测试对象：

1. `task006_near_neighbor`：近邻候选，检验 skill-use improvement 与继续演化路由。
2. `task008_bad_candidate`：坏 candidate，检验 skill-structure/problem negative outcome。
3. `task009_evaluator_gap`：evaluator 缺口，检验不要错误推进技能演化。
4. `task010_literature_required`：证据不足，检验 literature worker 路由。
5. `task011_portfolio_stop`：研究价值不足，检验 portfolio stop/pause 路由。

测试 runtime：

1. `pi_gpt55`
2. `pi_baidu_glm5`
3. `pi_baidu_kimi_k25`
4. `pi_baidu_minimax_m25`

初始矩阵暴露了一个真实的通用 harness 问题：

1. `pi_baidu_glm5/task006_near_neighbor` 输出了语义上合理但不在枚举中的 `problem_class = skill_use_improvement_not_structural`。
2. `pi_baidu_minimax_m25/task009_evaluator_gap` 输出了语义上合理但不在枚举中的 `recommended_next_worker = evaluator_repair_worker`。

这不是 provider/auth 问题，也不是 task-specific 逻辑问题，而是 LLM worker 与 deterministic contract 之间的边界问题。

修复原则：

1. 不让 controller 代写认知判断。
2. 不为某个 task 或某个模型加特殊补丁。
3. 由 deterministic verifier 给出 contract errors，再要求同一个 LLM worker 使用允许词表重新表达判断。
4. 把允许的 `problem_class`、`recommended_next_worker`、`recommended_action` 和 routing policy 显式注入 cognition worker prompt。

修复后，两个失败组合复跑通过：

```bash

  --runtimes pi_baidu_glm5 pi_baidu_minimax_m25 \
  --max-workers 2 \
  --timeout 240
```

随后完整矩阵复跑通过：

1. `pi_gpt55`: 5/5 passed。
2. `pi_baidu_glm5`: 5/5 passed。
3. `pi_baidu_kimi_k25`: 5/5 passed。
4. `pi_baidu_minimax_m25`: 5/5 passed。
5. 总计：20/20 passed。

关键产物：

1. `analysis/runtime_matrix/agent_runtime_matrix_report.yaml`
2. `analysis/runtime_matrix/agent_runtime_experiment_matrix.yaml`
3. `analysis/runtime_matrix/cases/{runtime}/{task}/`
4. `analysis/full_loop_validation/runs/{runtime}/`
5. `analysis/full_loop_validation/llm_worker_raw/{runtime}/`

这一步证明的内容：

1. 对当前 fixture task family，同一 `run_generic_loop_engine.py` 入口可以覆盖多 task。
2. 对当前 Pi runtime family，同一 `llm_full_loop_workers.py` 合约可以覆盖多 provider/model profile。
3. DaoShuGuo 没有复制 Pi 的 provider/auth 配置；它只引用 Pi profile 并负责研究 worker harness、契约校验、证据链和路由。
4. LLM worker 的输出不稳定是正常事实，通用框架必须具备 verifier-driven contract repair，而不是假设模型天然遵守 schema。

仍然不能声称的内容：

1. 不能声称 Codex/OMX framework-callable runtime 已经成立，`codex_omx` 仍在 registry 中标记为 blocked。
2. 不能声称 Level 5 research-quality autonomous cognition，当前仍是 fixture-level validation。
3. 不能声称不同模型的科研判断语义完全一致，本轮只证明 artifact chain 和 routing contract 均成立。

本轮最重要的认知：

通用自主科研框架的 runtime 泛化，不应该围绕 API/provider 写 adapter，而应该围绕 worker contract 和 verifier feedback 写 harness。Pi 负责模型和认证；DaoShuGuo 负责研究循环语义、对象契约、证据回链和失败可解释性。

## 113. 关键转折：从“闭环跑通”转向“认知规律发现”

在多 task × 多 Pi runtime 矩阵通过之后，我们讨论到一个更关键的问题：

> passed 不是终点。真正重要的是，多个 Agent 的科研认知是否可信、是否可比较、是否能从一致性与分歧中发现规律。

这意味着项目的关注点需要从“框架是否能跑通”升级为：

1. 不同 Agent 是否对同一科研状态形成一致判断。
2. 如果不一致，分歧发生在事实识别、问题分类、行动路由，还是研究价值判断。
3. 哪些分歧是合理的科研风格差异，哪些分歧暴露了 prompt/harness/schema/evaluator 的缺陷。
4. 这些分歧是否可以帮助我们改进技能、认知和成效交付，而不是只作为运行噪声被抹掉。

本轮矩阵已经暴露了几个可研究现象：

1. 大多数 runtime 对五类 fixture task 的 `problem_class` 形成了高度一致判断。
2. `task008_bad_candidate` 上，不同 runtime 对 `continue_loop` 的选择出现差异。有的认为坏 candidate 应继续修复，有的认为不应继续本轮循环。
3. `task009_evaluator_gap` 上，不同 runtime 对 evaluator repair 的责任边界有差异。有的路由到 `effectiveness_worker`，有的路由到 `adapter_repair_worker`。
4. MiniMax runtime 虽然通过率为 100%，但 latency 和 raw output 体量明显更高，说明“能通过”和“适合作为主循环 worker”不是同一个评价问题。

这些现象提醒我们：

1. contract-level pass 只能证明对象链和路由合法，不能证明认知完全一致。
2. 多 Agent 分歧不是坏事，但必须被结构化记录、比较、仲裁和反思。
3. 如果一个框架不能解释不同 Agent 为什么分歧，它就不能声称自己真正理解了科研认知过程。

因此，下一阶段不应继续简单堆 task 数量，而应建立三类能力：

1. `semantic agreement analyzer`
   - 比较不同 runtime 在同一 task 上的 `problem_class`、`recommended_next_worker`、`recommended_action`、`continue_loop`、`judgment_summary`。
   - 输出一致项、冲突项、轻微表达差异和严重语义分歧。

2. `disagreement adjudicator`
   - 当多个 runtime 都通过 contract，但判断不同，应触发仲裁。
   - 仲裁不是投票，而是基于证据链、任务边界、evaluator 状态、科研价值标准进行判断。
   - 仲裁结果应说明：接受哪种判断、拒绝哪种判断、还需要什么额外测试。

3. `pattern mining / cognition upgrade`
   - 从多个 task 和多个 runtime 的判断中提炼规律。
   - 例如：哪些任务容易引发 skill-use 与 skill-structure 混淆；哪些模型更容易过度延续循环；哪些模型更适合作为主 worker 或 second-opinion worker。
   - 将这些规律反向改进 prompt、schema、evaluator、routing policy 和 task onboarding。

这一步的研究意义很大：

如果我们能把多 Agent 的一致性和分歧变成可积累的认知资产，这个项目就不只是一个 agent harness，而开始成为“AI 辅助科研认知规律”的实验平台。

当前阶段性判断：

1. 框架骨架已经初步成立。
2. 多 runtime 认知输出已经具备可比较性。
3. 下一步必须研究“Agent 认知差异”本身，而不是继续满足于“所有脚本 passed”。

这也是本项目从工程验证进入科研验证的关键转折。

## 114. 主线校正：暂停扩大多 Agent 差异研究，转向真实科研闭环

在第 113 节之后，我们进一步确认：

多 Agent 语义差异是正常现象，不同 LLM 的能力、风格和判断边界本来就会不同。现在过早投入大量精力研究多智能体语义差异、对齐和仲裁，可能会偏离项目主线。

当前最重要的问题不是：

> 不同 Agent 为什么判断不同？

而是：

> 这个框架能否在一个真实科研任务上稳定运行多轮自主研究闭环，并且真的带来技能、认知和成效的提升？

因此，当前主线调整为：

1. 保留多 task × 多 runtime 矩阵作为 harness 稳定性证据。
2. 暂停扩大多 Agent 语义差异矩阵。
3. 选择一个真实科研任务作为 `real-task-001`。
4. 至少执行 3 轮 `skill -> effectiveness -> cognition -> routing/delivery` 闭环。
5. 观察多轮后是否出现：
   - 技能改善
   - 认知升级
   - 成效改进
   - claim 更准确
   - 成果路由更可信

本轮选择 `task004` 作为 `real-task-001` 的基础：

> 新能源接入下的 IEEE69 静态承载力评估。

选择原因：

1. 它已经有真实运行和 evaluator。
2. 它不是单纯 fixture，而是有明确电力科研意义的边界问题。
3. 它天然包含 `boundary overclaim` 风险，适合测试品味和成效层。
4. 它已有 task mismatch、skill mismatch、literature alignment、delivery routing 等历史资产。
5. 它能逼迫系统区分“指标提升”和“科研结论可信度提升”。

已经起草计划：

```text
plans/real-task-001-autonomous-research-loop-plan.md
```

该计划明确：

1. 不继续堆 task 数量。
2. 不追求多 runtime 差异研究。
3. 不允许 controller 下场改技能或写认知。

## 116. 真实科研闭环下一阶段收敛计划

当前系统已经能完成 claim gate，但还不能证明 cognition layer 已经像优秀研究生一样主动重构研究问题。

这一区分非常关键。

1. 阅读外部资料和文献方法谱系。

3. 判断 evaluator 是否表达了真正研究价值。
4. 判断 skill family 是否太窄。
5. 提出能落地的结构性技能、评价和场景升级。
6. 给出从 `diaomu` 走向 `zhuoshi` 所需的最低证据门槛。

因此，下一阶段不能简单继续 task004 多轮参数迭代。

继续增大 `q_step` 或扩展搜索范围，最多只能说明 skill-use condition 改变后是否更好，不能自动说明技能结构升级。

真正要验证的是：

> 当真实任务暴露出局部参数优化无法提高研究质量时，DaoShuGuo 能否引入外部学习，重构问题定义和方法空间，再让技能、评价和成效进入下一轮更高质量闭环。
