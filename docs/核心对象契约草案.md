# 核心对象契约草案

## 1. 文档目的

本文件给出第一批核心事实层对象的具体契约草案。

这些对象是后续所有运行、证据、认知和报告的事实基础，因此优先定义：

1. `Task`
2. `Evaluator`
3. `Run`

本文件仍然是 spec，不是最终实现格式。

## 2. 设计定位

这三个对象属于事实层对象。

它们的职责分别是：

- `Task`：定义要研究什么。
- `Evaluator`：定义怎样算进步。
- `Run`：记录某次实际发生了什么。

它们必须尽可能少受表达层和总结层影响。

## 3. 通用封套

所有核心对象建议都具备统一封套。

### 3.1 必备公共字段

- `schema_version`
- `object_type`
- `object_id`
- `object_version`
- `created_at`
- `updated_at`
- `status`
- `metadata`

### 3.2 推荐公共字段

- `title`
- `description`
- `tags`
- `extensions`
- `experimental`

### 3.3 设计说明

- `object_id` 用于稳定身份。
- `object_version` 用于内容演化。
- `schema_version` 用于解析结构。
- `metadata` 用于非核心但稳定的附加信息。
- `experimental` 用于当前阶段临时研究字段，不应污染稳定核心字段。

## 4. Task 契约草案

### 4.1 对象意义

`Task` 用于表达一个研究任务的稳定定义。

它不是运行日志，也不是报告摘要。

### 4.2 Task 必填核心

- `object_id`
- `object_version`
- `title`
- `research_object`
- `problem_statement`
- `scenario_boundary`
- `success_intent`
- `baseline_refs`
- `constraint_summary`

### 4.3 Task 建议字段

- `motivation`
- `importance_level`
- `domain_context`
- `input_artifacts`
- `target_metrics`
- `risk_hypotheses`
- `assumptions`
- `owner_notes`

### 4.4 字段语义建议

- `research_object`
  表达研究对象本体，例如配电网、微网、特定调度问题。

- `problem_statement`
  表达本轮任务究竟试图解决什么问题。

- `scenario_boundary`
  表达在哪些条件下研究该问题。

- `success_intent`
  表达目标方向，而不是具体 evaluator 结果。

- `baseline_refs`
  指向一个或多个基线对象或基线定义。

- `constraint_summary`
  表达不可忽视的约束，例如算力、数据、工程边界、物理约束。

### 4.5 Task 典型形态

```yaml
schema_version: "0.1"
object_type: "task"
object_id: "task001"
object_version: "0.1.0"
title: "IEEE33无功优化最小闭环验证"
research_object: "IEEE 33节点配电网无功优化问题"
problem_statement: "在给定工况与约束下提升电压质量并降低损耗"
scenario_boundary:
  grid_model: "ieee33"
  operating_conditions: ["normal_load"]
success_intent:
  goal: "相对基线获得可重复改进"
baseline_refs: ["baseline.task001.default"]
constraint_summary:
  physical: ["电压约束", "无功补偿边界"]
  engineering: ["使用可编程仿真环境"]
metadata: {}
```

### 4.6 Task 校验规则

- 没有 `research_object` 的任务无效。
- 没有 `scenario_boundary` 的任务不得进入 evaluator 编译。
- 没有 `baseline_refs` 的任务不得进入正式成效比较。
- `success_intent` 不能直接写成研究结论。

## 5. Evaluator 契约草案

### 5.1 对象意义

`Evaluator` 用于表达成效判断逻辑。

它必须独立于技能实现存在，不能被某个具体算法绑死。

### 5.2 Evaluator 必填核心

- `object_id`
- `object_version`
- `task_ref`
- `evaluation_goal`
- `metric_definitions`
- `baseline_strategy`
- `pass_criteria`
- `execution_entry`

### 5.3 Evaluator 建议字段

- `preconditions`
- `postconditions`
- `failure_modes`
- `comparison_mode`
- `stability_checks`
- `blind_spots`
- `evidence_outputs`

### 5.4 字段语义建议

- `task_ref`
  指向该 evaluator 服务的任务定义。

- `evaluation_goal`
  用一句话说明这个 evaluator 要证明什么。

- `metric_definitions`
  定义指标名、含义、方向、单位和计算方式。

- `baseline_strategy`
  定义如何获取比较对象。

- `pass_criteria`
  定义什么条件下可认为本轮结果有效。

- `execution_entry`
  指向 evaluator 的执行入口，例如脚本、命令或函数。

### 5.5 Evaluator 典型形态

```yaml
schema_version: "0.1"
object_type: "evaluator"
object_id: "evaluator.task001.default"
object_version: "0.1.0"
task_ref: "task001"
evaluation_goal: "验证候选方法是否相对基线改进电压质量与网损"
metric_definitions:
  - metric_id: "loss"
    direction: "lower_is_better"
    unit: "kW"
  - metric_id: "voltage_deviation"
    direction: "lower_is_better"
    unit: "p.u."
baseline_strategy:
  type: "named_baseline"
  refs: ["baseline.task001.default"]
pass_criteria:
  rule: "关键指标优于基线且结果可复现"
execution_entry:
  type: "python_script"
  path: "evaluators/task001_evaluator.py"
metadata: {}
```

### 5.6 Evaluator 校验规则

- 没有 `task_ref` 的 evaluator 无效。
- 没有 `metric_definitions` 的 evaluator 无法比较。
- 没有 `baseline_strategy` 的 evaluator 不得声称进步。
- `pass_criteria` 不能仅写成“效果更好”。

## 6. Run 契约草案

### 6.1 对象意义

`Run` 用于记录一次真实发生的执行尝试。

它是系统里的运行事实对象，不是总结，不是解释。

### 6.2 Run 必填核心

- `object_id`
- `object_version`
- `task_ref`
- `evaluator_ref`
- `run_status`
- `started_at`
- `input_snapshot`
- `skill_refs`
- `result_summary`

### 6.3 Run 建议字段

- `ended_at`
- `attempt_index`
- `parent_run_ref`
- `trigger_reason`
- `artifact_refs`
- `failure_summary`
- `log_refs`
- `environment_summary`
- `agent_trace_refs`

### 6.4 字段语义建议

- `task_ref`
  指向本次运行服务的任务。

- `evaluator_ref`
  指向本次运行采用的 evaluator。

- `run_status`
  表示该次运行状态，例如 `completed`、`failed_experiment`、`insufficient_evidence`。

- `input_snapshot`
  表达该次运行在开始时使用的关键输入快照。

- `skill_refs`
  列出本次运行使用或生成的技能引用。

- `result_summary`
  只表达结构化结果摘要，不表达高层价值判断。

### 6.5 Run 典型形态

```yaml
schema_version: "0.1"
object_type: "run"
object_id: "run.task001.0001"
object_version: "0.1.0"
task_ref: "task001"
evaluator_ref: "evaluator.task001.default"
run_status: "completed"
started_at: "2026-04-19T12:00:00Z"
input_snapshot:
  task_version: "0.1.0"
  evaluator_version: "0.1.0"
skill_refs:
  used: ["skill.baseline_solver@0.1.0"]
  produced: ["skill.reactive_optimizer_candidate@0.1.0"]
result_summary:
  metrics:
    loss: 123.4
    voltage_deviation: 0.032
  baseline_comparison: "improved"
metadata: {}
```

### 6.6 Run 校验规则

- 没有 `task_ref` 或 `evaluator_ref` 的 run 不成立。
- `run_status` 必须来自受控枚举，而不是任意文本。
- `result_summary` 只能写事实摘要，不能出现“重大创新”之类表达。
- 若 `run_status` 为完成态，必须存在对应结果摘要。

## 7. 三类对象之间的最小引用要求

第一阶段至少应满足：

- `Evaluator.task_ref -> Task.object_id`
- `Run.task_ref -> Task.object_id`
- `Run.evaluator_ref -> Evaluator.object_id`

必要时还可以增加：

- `Run.parent_run_ref`
- `Task.related_task_refs`

## 8. 事实层对象的边界警戒线

以下情况说明事实层契约开始污染：

1. Task 中开始写“本轮已经证明了什么”。
2. Evaluator 中开始写“为什么这个方法理论上更好”。
3. Run 中开始写“因此我们获得了新认知”。
4. 事实层对象里直接出现玉、石、木、墨分级。

这些内容都应留给派生对象或表达对象。
