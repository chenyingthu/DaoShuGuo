# 系统模块设计

## 1. 文档目的

本文件用于明确项目中各核心模块的职责边界、输入输出、相互依赖和演进优先级。

它回答的问题不是“系统最终会长成什么样”，而是“当前阶段哪些模块必须存在，它们各自负责什么，不能互相替代什么”。

## 2. 模块设计原则

### 2.1 单一职责

每个模块必须优先承担一类核心责任，避免将“评价、执行、解释、写作”混成一个黑箱。

### 2.2 可替换

模块边界应允许未来替换底层模型、仿真器、技能实现方式和认知存储方式，而不破坏整体闭环。

### 2.3 可审计

模块输出必须足够结构化，以便后续回看任务是否真的产生了成效、技能或认知。

### 2.4 先轻量后复杂

第一阶段优先采用文件、目录、脚本和轻量 registry，不把复杂度前置到基础验证之前。

### 2.5 面向能力应用演化

当前模块边界不应只服务于单体系统内部清晰，还应服务于未来演化为独立能力应用：

- 可独立运行
- 可独立测试
- 可独立失败
- 通过统一对象契约协同

## 3. 核心模块

### 3.1 Task Framing 模块

职责：

- 接收研究意图
- 明确问题定义
- 识别研究对象、约束、场景和价值
- 输出任务包

输入：

- 人类研究意图
- 领域背景
- 历史任务经验

输出：

- 任务说明
- 约束集
- 初始目标
- 候选风险列表

禁止替代：

- 不负责写技能实现
- 不负责做结果评价
- 不负责生成认知结论

### 3.2 Effectiveness Engine 模块

职责：

- 将研究目标编译为 evaluator
- 定义指标、阈值和比较逻辑
- 对技能输出做独立评价
- 输出结构化结果和基线比较

输入：

- 任务包
- 基线
- 技能执行结果

输出：

- 指标结果
- 通过/未通过
- 与基线差异
- 稳定性信息

禁止替代：

- 不直接参与技能开发
- 不参与认知解释
- 不输出研究价值判断

### 3.3 Skill Manager 模块

职责：

- 检索已有技能
- 组装技能链
- 记录技能适用条件
- 固化成功技能

输入：

- 任务包
- 认知约束
- evaluator 反馈

输出：

- 技能调用计划
- 新技能草案
- 技能版本记录
- 技能写回动作

禁止替代：

- 不负责定义指标
- 不负责决定成果等级
- 不负责理论化解释

### 3.4 Skill Builder 模块

职责：

- 在已有技能不足时构建新技能
- 在 evaluator 反馈下迭代实现
- 产出可运行的技能候选

输入：

- 技能调用计划
- evaluator 失败原因
- 任务约束

输出：

- 新技能实现
- 修改记录
- 预期改进点

禁止替代：

- 不负责最终评价
- 不负责认知抽象

### 3.5 Cognition Manager 模块

职责：

- 检索已有认知
- 提供问题相关语境
- 维护认知关系
- 管理候选认知与稳定认知

输入：

- 任务包
- 历史认知
- 结果解释

输出：

- 认知子集
- 认知冲突提示
- 认知写回动作

禁止替代：

- 不负责技能执行
- 不负责成果分级

### 3.6 Cognition Analyst 模块

职责：

- 对有效或失败结果做机制解释
- 提炼认知候选
- 明确边界与不确定性

输入：

- evaluator 结果
- 对比基线
- 技能实现信息
- 历史认知

输出：

- 认知卡片候选
- 失败认知
- 机理解释摘要

禁止替代：

- 不负责宣布成果等级
- 不负责美化写作

### 3.7 Taste Grader 模块

职责：

- 对结果做“拓玉 / 琢石 / 雕木 / 绘墨”分级
- 判断 claim 上限
- 对报告输出施加约束

输入：

- evaluator 结果
- 基线对比
- 复现情况
- 认知解释

输出：

- 成果等级
- 等级理由
- 风险提示
- 表达上限

禁止替代：

- 不直接生成报告正文
- 不参与技能实现

### 3.8 Claim Guard 模块

职责：

- 审核最终报告中的主张强度
- 检测是否越过成果等级允许的表达边界

输入：

- 成果等级
- 报告草稿
- 证据摘要

输出：

- claim 审核意见
- 降级建议
- 禁止表达项

### 3.9 Evidence Binder 模块

职责：

- 将任务、代码、实验、结果、认知和报告绑定成证据链
- 支撑后续复盘和研究分析

输入：

- 运行轨迹
- evaluator 输出
- 技能版本
- 认知卡片

输出：

- 证据包
- 回链索引
- 任务级研究档案

### 3.10 Literature Alignment 模块

职责：

- 检索相关文献
- 提取已有方法与已有解释
- 将本地技能和认知映射到文献语义空间
- 为新颖性判断提供外部参照

输入：

- 技能对象
- 认知对象
- strategy_comparison

输出：

- literature_alignment 对象
- 方法关系判断
- 理论关系判断
- 新颖性提示

禁止替代：

- 不负责本地实验执行
- 不负责改写 evaluator 结果

### 3.11 Comparative Cognition Upgrade 模块

职责：

- 比较技能语义层次
- 比较认知解释层次
- 决定认知的晋升、降级或冻结
- 对 claim ceiling 形成反馈

输入：

- strategy_comparison
- cognition
- literature_alignment
- evidence_bundle

输出：

- strategy_semantic_comparison
- novelty_assessment
- cognition_upgrade
- upgraded_cognition

禁止替代：

- 不负责产生原始实验事实
- 不直接替代 Report Gate

## 4. Orchestrator 的定位

Orchestrator 不是“超级智能模块”，而是“阶段切换与约束执行模块”。

它的职责是：

1. 调用正确模块。
2. 按顺序推进状态。
3. 判断阶段是否可结束。
4. 决定哪些结果可以写回。
5. 保证证据链不丢失。

它不应该承担：

- 科学判断本体
- 技能设计本体
- 认知解释本体

随着系统演化，Orchestrator 应逐步退化为：

- 路由器
- 协调器
- 写回与监控器

而不是所有能力的宿主。

## 5. 第一阶段模块优先级

第一阶段必须实现：

1. Task Framing
2. Effectiveness Engine
3. Skill Manager
4. Skill Builder
5. Cognition Analyst
6. Taste Grader
7. Evidence Binder
8. Orchestrator

第一阶段可以简化：

- Cognition Manager 的复杂图检索
- Claim Guard 的细粒度语义审查
- 多任务共享调度
- Literature Alignment
- Comparative Cognition Upgrade

## 6. 模块间依赖关系

推荐依赖顺序：

1. Task Framing -> Effectiveness Engine
2. Task Framing -> Cognition Manager
3. Cognition Manager -> Skill Manager
4. Skill Manager -> Skill Builder
5. Skill Builder -> Effectiveness Engine
6. Effectiveness Engine -> Cognition Analyst
7. Effectiveness Engine + Cognition Analyst -> Taste Grader
8. 全部结果 -> Evidence Binder
9. strategy_comparison -> Literature Alignment
10. strategy_comparison + literature_alignment + cognition -> Comparative Cognition Upgrade

Taste Grader 必须晚于 evaluator，但早于正式报告。

## 8. 面向解耦与自律协同的模块要求

本项目的长期目标不是“模块化单体系统”，而是：

- 模块能够独立运行
- 模块能够独立测试
- 模块能够独立失败
- 模块通过统一对象契约进行分散自律协同

因此，当前模块设计必须尽量避免：

- 共享可变内部状态
- 隐式依赖链
- 由 orchestrator 承担所有能力本体

## 7. 设计上的警戒线

以下情况说明模块边界开始退化：

1. evaluator 开始负责解释“为什么有效”。
2. Skill Builder 在没有 evaluator 的情况下自行判定成功。
3. Cognition Analyst 开始越权给出夸大结论。
4. Orchestrator 变成所有逻辑的杂物箱。
5. Report 模块反过来修改成果等级。

若出现上述情况，应优先重构边界，而不是继续堆功能。
